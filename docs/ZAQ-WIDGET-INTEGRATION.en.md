# ZAQ web widget: integration status

Source: <https://github.com/www-zaq-ai/web_widget/blob/main/docs/integration-guideline.md>

Status: **implemented and working on `localhost:4321`** with the temporary ngrok URL. Not yet tested on a Vercel preview (the CSP does not apply under `pnpm dev`). This file started as a feasibility note; it now records what the widget requires, what we built, and what is still open.

## What the Zaq documentation says

- `embed.js` creates its own `<iframe id="zaq-widget">`, inside the container named by the `iframe-location-id` attribute (that attribute is not in the public guide; it comes from the Zaq contact).
- Identity goes **only through a signed JWT (HS256)** produced by a backend. Claims: `widget_id`, `user_id` (non-blank, 255 bytes max), `conversation_id` (or null), `prompt_context` (free text, 100,000 bytes max), `iss`, `aud`, `iat`, `exp` (300 s max), `jti` (16 to 255 characters). The front end then calls `zaq.widget.init({ identity_token })`.
- The backend endpoint is expected at `POST /api/widget-identity` and returns `{ "identity_token": "<JWT>" }` with `Cache-Control: no-store`.
- The widget emits two events on the iframe element: `zaq:conversation` (first accepted question, `detail: { conversation_id }`) and `zaq:authentication-required` (token expired; fetch a new token and call `init` again).
- `getSettings()` / `updateSettings()` accept `theme` (`light`, `dark`, `auto`) and `language` (`en`, `fr`, `ar`).
- The allowed embedding origins are configured in the Zaq back office (`/bo/channels/retrieval/web_widget`): scheme and non-default port included, no path.
- The guide says nothing about CSP directives, storage, iframe sizing, or any framework.

## What we built

| Need | Solution |
| --- | --- |
| Backend to sign the JWT | `src/pages/api/widget-identity.ts`, the only on-demand route (`prerender = false`), via the `@astrojs/vercel` adapter. The rest of the site stays static. |
| Signing | HS256 with `node:crypto` (no JWT library), 7-day lifetime, random `jti`. Code in `src/lib/zaq-identity.ts`. |
| Secrets | `ZAQ_SIGNING_KEY`, `ZAQ_ISSUER`, `ZAQ_AUDIENCE` as server-only `astro:env` secrets (`.env` locally, Vercel environment variables when deployed). |
| `user_id` | UUID v4 generated by the endpoint and kept in a server-set `HttpOnly` `userID` cookie, so a returning visitor is recognised and Zaq can show their history. |
| `conversation_id` | `conversationId` cookie written by the browser on `zaq:conversation`, read back by the endpoint. |
| Municipality | No code parameter exists. `prompt_context` is the constant `Saint-Saturnin 63450`. |
| Front end | `src/scripts/zaq-widget.ts`: waits for `zaq.widget`, sets dark/fr, fetches a token, calls `init`, and renews the token on `zaq:authentication-required`. |
| Markup and layout | `src/components/ZaqWidget.astro`: container `#iframe-zaq`, the `embed.js` tag (URL from `PUBLIC_ZAQ_URL`), global styles that make the iframe fill the space between header and footer, and a welcome block (logo and intro text) behind the transparent iframe. |
| CSP | `vercel.json` allows the Zaq origin in `script-src`, `frame-src` and `connect-src` (plus `wss:`). A test keeps it in line with `PUBLIC_ZAQ_URL` in `.env.example`. |

The earlier iframe-based integration (`ChatFrame`, `chat-frame.ts`, municipality code and `userID` in URL parameters) was **removed**; it stays in the Git history.

## Decisions that changed because of Zaq

1. **A backend is now required.** The site is no longer purely static: one serverless function signs the token. "No adapter" was dropped.
2. **Third-party script.** The "no third-party scripts" rule no longer holds: Zaq's script runs in our page with access to its DOM and non-HttpOnly cookies. Trust in that code has to be validated.
3. **Cookies.** The site now sets two first-party cookies (`userID`, `conversationId`) instead of one, and the `userID` is tied to a conversation history. The RGPD analysis needs to be redone.
4. **Identity model.** Zaq only needs a non-blank `user_id`, so a random pseudonymous ID is enough; no login is needed.

## Still open

- **Vercel preview test** with the CSP active. `img-src`, `style-src` and `font-src` may need the Zaq host. The ngrok host may show a warning page to real visitors.
- **Stable Zaq URLs** (production and preview). The ngrok URL is temporary, and allowing it in the CSP is a risk if the subdomain is reassigned.
- **`iss` and `aud`**: we use the guide's example values (`test-widget`, `zaq-web-widget`). Confirm the real ones.
- **Allowed origins**: add `http://localhost:4321`, the Vercel previews and the final domain.
- **Conversation ownership**: does Zaq check that `conversation_id` belongs to the token's `user_id`? The cookie can be edited by the visitor.
- **Abuse protection**: the endpoint can be called by any script that forges the `Origin` header, creating unlimited users. We need rate limiting on our side and a cap on Zaq's side.
- **Storage and cookies**: does the widget write cookies or `sessionStorage` in our origin? (The guide's example uses `sessionStorage` on the integrator side; we use a cookie.)
- **Styling**: can the widget's colours, fonts or radius be set per widget or passed from the site (through `init`, a JWT claim or `postMessage`)? Which `updateSettings` options exist beyond `theme` and `language`? Can the iframe's size and position be controlled?
- **RGPD**: consent, cookie lifetime, legal notices and privacy policy, with the person in charge of the legal side.

See `CLAUDE.md` for the project-wide decisions and `SECURITY-AUDIT.md` (local, git-ignored) for the risk review.
